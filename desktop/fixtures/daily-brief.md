**SQLite locking modes and WAL.** `database is locked` with a single process almost always means there are more connections than you think, not that SQLite is broken. In the default rollback-journal mode a write takes an exclusive lock over the whole database file for the duration of the commit, so even a read opened at the wrong moment collides with it. The classic culprit is a migration runner: its own connection, a `BEGIN` that never reached `COMMIT`, and the application's connection queuing behind it until the driver gives up. Switching to write-ahead logging with `PRAGMA journal_mode=WAL` lets readers work from a snapshot while the single writer appends to the `-wal` file, and `busy_timeout` makes collisions wait instead of fail. Rule of thumb: "database is locked" with one process means a connection you forgot about — hunt for the second handle or the unfinished transaction before blaming SQLite.

**EADDRINUSE, TIME_WAIT, and `SO_REUSEADDR`.** "Address already in use" after a restart means the kernel still has a socket on that port. Half the time it's mundane: the previous dev server didn't fully die and a stale process still holds the port, so `lsof -i :1420` finds the PID and the restart works. The other half is TIME_WAIT: when a TCP connection closes, the side that initiated it keeps the connection state for about 60 seconds so late packets can't corrupt a new connection on the same port, which can make an immediate rebind fail even though nothing is listening. Servers opt out with `SO_REUSEADDR`, which lets a bind succeed over those sockets. Rule of thumb: address-in-use after a restart means something from the last run survived — check `lsof` before blaming the bundler.

**Shell quoting and expansion order.** `"${VAR}"` inside double quotes is expanded by the shell when the line runs, so the value is whatever `VAR` holds at that moment; inside single quotes nothing is expanded at all — the script literally contains the string `${VAR}`, and whatever executes it on the far side (ssh, docker exec) does the expansion. A variable that shows up empty in `set -x` output is usually set in the caller's environment but never exported, so the child script never sees it. Rule of thumb: when a variable is mysteriously empty, print `env | grep VAR` inside the script that consumed it — if it's absent there, the bug is the caller's missing `export`, not the quoting.

**APNs and PDP contexts.** A cellular modem doesn't get IP data just because a SIM registered on the network. An APN (Access Point Name) names the carrier gateway the data connection attaches to; consumer SIMs have it baked in during provisioning, which is why phones never mention it, while IoT SIMs expect the device firmware to state it explicitly — hence the `AT+CGDCONT=1,"IP","hologram"` line: context ID 1, IPv4, APN string, sent over the modem's UART before anything else. Defining it isn't enough either; `AT+CGACT=1,1` activates the context, and without a defined context there's nothing to activate. Rule of thumb: carrier dashboard says connected but no data means the APN was never set — check `AT+CGDCONT?` before anything else.

**Container CA bundles.** `x509: certificate signed by unknown authority` inside a container, when the same request works from your laptop, is almost never about the certificate. A TLS client verifies the server's chain against a local list of roots; your OS ships one, and minimal container images deliberately don't — so the Go binary finds no roots under `/etc/ssl/certs` and every chain fails. Adding the `ca-certificates` package in the Dockerfile generates the concatenated PEM bundle the system verifier reads, no code change needed. If the upstream is signed by a private CA (a corporate proxy, a self-managed intermediate), the public bundle won't ever contain that root and you must append it yourself. Rule of thumb: "unknown authority" in a container is a missing CA bundle nine times out of ten; check the image before touching the code.

**React StrictMode's double mount.** In development, StrictMode mounts, unmounts, and remounts every component once, and runs `useEffect` twice — on purpose. Effects whose cleanup is missing produce real bugs, and the double cycle makes them impossible to miss: the effect runs, its cleanup runs, it runs again, and anything that only works when it runs exactly once (an un-cancelled fetch, a never-torn-down subscription) now visibly misbehaves. Production builds skip the cycle entirely; the same component mounts once. The fix isn't removing `<React.StrictMode>` but writing the effect honestly: return a cleanup that cancels in-flight work, and make the effect idempotent. Rule of thumb: an effect that only works when it runs exactly once is a bug wearing a workaround.
